> 2026-09-09 공개 이관본. 초기 문서 제작 계획이며, 이후 합의된 120초 스토리라인은 `docs/demo/storyboard.md`가 기준이다. 기기별 절대 경로와 내부 실행 식별자는 제외했다. 원본은 변경하지 않았다.

## Requirements Summary

- 요청: 새 브랜치에서 PR 유형·실제 오픈소스 PR 사례·참고할 연구와 2분 콘티 초안을 작성하고 검토해 개선한다. 실행 코드 수정·배포·영상 제작은 이번 범위가 아니다.
- 작업 디렉터리: 당시 `the-last-human` 문서 작업용 worktree; 시작 SHA `2210cb5`, 작업 트리 깨끗함. 새 브랜치 제안: `docs/pr-types-storyboard`.
- 저장소 산출물은 `docs/pr-types.md`, `docs/demo/storyboard.md` 두 개다. 자료 조사에서 확인한 출처와 적용 판단은 전자에, 장면·메시지·완전한 영어 대본·전제는 후자에 둔다.
- 사용자가 정한 질문 방향: PR 목적 → 전체 기능/구조 → 변경 유형별 의도와 영향. 코드 세부는 설명의 근거이지 퀴즈의 중심이 아니다.
- 아키텍처 설계/도입/전환을 명시적으로 다룬다. 목적·구조 범위·호환성/실패/데이터 영향은 서로 다른 축이며, 복합 PR을 하나의 배타적 라벨로 강제하지 않는다.
- 사용자 승인 없는 위험 가중치·질문 생성 프롬프트·pass/hold 기준·attestation schema를 작성/변경하지 않는다. 협의용 질문 관점/예시는 최종 정책과 구분한다.
- 개인 점수·등급·순위·조직 개인별 집계·팀장 조회·보류 영구 저장 금지. 위험도 기반 적용, 저위험 neutral, Action의 독립 위험 재계산과 현재 SHA 확인 유지(`.github/copilot-instructions.md:6-21,39-48`).
- 핵심 고객은 PR 작성자다. 사람이 책임에 필요한 목적·구조·영향을 설명하고 특정 revision에 근거를 남기는 것이 목표이며, 무보조 답변·완전한 이해·결함 없음의 증명을 주장하지 않는다.
- 기존 금요일 데모 계획의 1인 기본, 질문 기본 3개, 웹 직접 제출, Azure 연계, 영어 TTS 방향을 계승한다. 모든 실제 리소스/구현 상태는 미완료로 구분한다.
- 빠른 초안 우선: 사례 전수조사·완전한 PR 분류 표준·수상 확률 계산을 시도하지 않는다. 공개 자료만 새 문서에 인용하고 사내 회의/챌린지 전문·개인정보를 저장소로 옮기지 않는다.
- 계획 검토 기본 1라운드 후 사용자가 요청한 문서 초안을 작성한다.

## Acceptance Criteria (testable, verifiable — register each as a Task during implementation)

- AC1: 기존 변경을 보존하고 새 `docs/pr-types-storyboard` 브랜치(충돌 시 비파괴 접미사)를 만든다. commit/push/외부 PR 게시를 하지 않는다.
- AC2: `docs/demo/storyboard.md`에 핵심 메시지와 대상, 총 120초 이하의 연속 시간표 초안을 작성한다. 장면마다 전달 메시지·보여줄 화면·행동/증거·영어 내레이션·미구현 전제를 포함한다.
- AC3: `docs/pr-types.md`에 약 10–12개의 변화 관점과 다축 분류 방법, 아키텍처 설계 문서 PR vs 구현 PR vs 구조 보존 리팩터링의 차이를 정리한다. 자동 분류 enum/모델/가중치를 결정하지 않는다.
- AC4: 최소 8개 실제 공개 OSS PR을 정확한 owner/repo/number·제목·상태/시점·URL·변경 근거와 함께 정리한다. 아키텍처 예시 2개 이상을 포함하며, 설계 제안과 구현/릴리스 완료를 구분한다. 각 예시에 목적·구조·의도 질문 관점과 배울 점을 연결한다.
- AC5: 관련 연구/전문가 자료 최소 3개를 원문 서지/DOI/공식 페이지로 확인한다. 각각 직접 뒷받침하는 주장·연구 대상/한계·우리 설계에 대한 추론을 구분하고 개인 이해 점수나 제품 효과 수치로 전용하지 않는다.
- AC6: PR 연구를 바탕으로 콘티를 정렬한다. 대표 장면은 현재 retry 샘플을 우선 사용하고, 실제 OSS PR은 조사 근거이지 The Last Human을 사용했다는 시연 증거가 아니다. 현재와 목표 구현, 모의 화면과 실제 화면, 편집 시간 압축을 구분한다.
- AC7: GitHub/Copilot/Azure 연결은 공식 기능과 새로 구현해야 하는 제품 동작을 구분한다. 기계 발급자와 사람 확인자·SHA·질문 근거·성공 기록·구역 집계의 연결을 장면에 명시한다. 개인 보류 원문을 공개 댓글/로그/영상에 남기는 장면은 없다.
- AC8: 완성된 두 초안을 독립 검토하고 사실 오류·과장·중복·시간 초과·정책 충돌을 수정한다. 확인하지 못한 외부 정보는 단정하지 않으며 남은 인간 결정은 문서 끝에 행동을 바꾸는 항목만 남긴다.

## Mathematical Specification (if applicable)

- 비자명한 수학은 없다. 영상은 각 행의 `start_seconds`/`end_seconds`로 표현하고 인접 행의 끝/시작이 일치해야 한다.

### P2. 공개 PR/연구 조사

- OSS PR 조사와 논문 조사는 별도 읽기 전용 조사로 나눌 수 있다. 저장소 코드·내부 문서를 외부 서비스에 전송하지 않는다. 공개 검색 질의만 사용한다.
- PR 제목/라벨만으로 분류하지 않고 본문과 변경 파일/구현 또는 설계 내용을 확인한다. 병합 여부와 실제 기능 도입/릴리스는 구별한다.
- 대형 PR 전체를 복사하지 않고 근거 파일이나 설계 절을 특정해 짧게 요약한다. PR/연구별 직접 관찰과 우리의 질문 설계 추론을 구분한다.
- 학술 후보는 변경 목적, tangled changes, 현대 코드 리뷰의 이해/지식 공유, 아키텍처 결정 기록이다. ADR 관행 글은 논문과 구분한다.

### P3. 두 문서 초안

- `docs/pr-types.md`: 먼저 분류의 목적·세 축, 다음 변화 관점, 실제 PR 사례, 연구 근거, 적용 제한과 남은 결정 순서로 작성한다.
- `docs/demo/storyboard.md`: 먼저 2분 안에 보여줄 하나의 가치, 다음 시간표/전체 영어 대본, 화면별 실제 구현 전제, 촬영·편집 시 지킬 경계, 남은 승인 순서로 작성한다.
- 콘티는 PR 목적/구조/의도 설명이 중심이고 코드의 세부 동작은 그 설명을 뒷받침하는 짧은 근거로 배치한다. 마지막의 확인 기록/머지/구역 집계를 같은 revision의 사실로 연결한다.
- MS 강점은 Copilot 작성→GitHub PR의 인간 확인→머지 제어→Azure 운영의 연결이다. 공개 API의 기술적 독점성이나 다른 제품에 해당 기능이 없다는 전수조사 주장을 하지 않는다.

### P4. 초안 교차 검토

- 콘텐츠 검토자는 실제 두 문서의 사실 근거, 다축 모델, 아키텍처 범위, 정책과 영상 주장/화면 대응을 확인한다.
- 수정은 위 두 파일과 이 계획 파일에만 한정한다. 코드·워크플로·공개 PR·사내 ideation 문서는 수정하지 않는다.
- 초안에 아직 없는 외부 자료를 지어내 채우지 않는다. 분류는 보편 표준이 아닌 초기 작업 모델임을 표시한다.

## Risks & Mitigations

- 자료 조사가 콘티 작성을 지연: OSS 8–10건, 연구 3–4건의 대표 표본으로 제한하고 메시지/장면 초안은 먼저 잡는다.
- “아키텍처”를 큰 diff/리팩터링과 혼동: 경계·책임·의존·배포 구조·결정 이유가 바뀌는지를 근거로 설명한다.
- PR 분류의 배타성/과도한 세분화: 목적과 구조/영향을 분리하고 여러 관점이 동시에 적용되는 예시를 든다.
- 오픈소스 제품에 대한 오해: 공개 PR을 이 제품의 사용자·실패 사례처럼 연출하지 않고 학습용 참고로만 쓴다.
- 위조된 성공 화면: 장면은 목표 상태로 쓰고 필요한 구현/원본 증거가 없으면 촬영 완료로 간주하지 않는다.
- 영상에 개인 답변/보류 이력이 남음: 허가된 데모 계정·합성 답변만 사용하고 실제 사용자 보류 원문·식별 정보를 기록하지 않는다.
- 연구의 과잉 일반화: commit-level 연구를 PR 분류의 정답/사람 이해 측정 표준으로 주장하지 않는다.
- 리뷰 반복으로 초안 지연: 계획 1라운드, 문서 콘텐츠 1라운드에서 범위에 필요한 수정만 수행한다.

## Verification Steps

- PR 링크의 저장소/번호/제목/상태와 최소한의 본문·변경 파일 근거를 대조한다. 다른 저장소 PR 표기는 항상 `owner/repo#number`다.
- 연구 출처의 실제 제목/저자/연도·대상·주장과 요약을 대조한다. 통계가 필요하지 않으면 수치를 인용하지 않는다.
- 시간표의 연속성/양수 길이/합계 <=120초와 영어 대본의 누락 여부를 간단한 로컬 계산으로 확인한다. 새 lint/test 도구는 설치하지 않는다.
- 두 문서의 링크·주력 PR·메시지·미구현 표시가 일치하는지 확인한다.
- `git diff --check`, `git status`, 신규 파일 diff로 문서 이외 변경이 없는지 확인한다. 문서만 변경하므로 애플리케이션 테스트/빌드는 실행하지 않는다.
