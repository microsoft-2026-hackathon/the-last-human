### 현재 구현 방향

이미 있는 Python 코어를 폐기할 근거는 발견되지 않았다. 차이는 코어의 존재 여부보다 **정적 페이지·댓글 기반 프로토타입을 로그인 웹 제출·신뢰된 발급·현재 커밋 체크로 연결하는 런타임**에 있다.

```text
GitHub Actions (PR 이벤트)
  -> cli.score -> diff/config/risk -> 위험도·앵커
  -> cli.page  -> structure/interview/webui -> 질문 JSON + 정적 HTML
                                                   |
                                     브라우저 답변 복사
                                                   |
                                     사람이 PR 댓글 제출
                                                   v
GitHub Actions (issue_comment 이벤트)
  -> cli.grade -> interview -> attest -> bot 결과 댓글
  -> cli.gate  -> 현재 위험도 재계산 + 인증/SHA 대조 -> commit status

GitHub Actions (main push / schedule)
  -> GitHub PR/상태/댓글 수집 -> cli.dashboard -> ledger/dashboard -> Pages
```

`cli.py`는 Python 측 진입점이고 GitHub 작업은 주로 YAML 안의 `gh` 호출로 연결된다. 위험 계산은 모델과 분리되어 있지만, `interview.py`의 모델 호출까지 순수 함수라는 뜻은 아니다.

- **제품 문서에 확정 범위로 적힌 것:** Python 재사용, Azure 백엔드와 웹 대시보드, VS Code 확장 제외, 기본 질문 3개, 유효한 확인자 1인 기본, 금요일 영상 목표.

### 증거와 확신

- D1: code trace + 실제 함수 진단, HIGH confidence. 초기 HIGH를 기존 코드 관찰인 MEDIUM으로 기록한다.
- D2: code trace + [공식 action 입력 계약](https://github.com/actions/download-artifact/blob/v4/action.yml), HIGH confidence. S4의 미확인 추론을 계약상 결함으로 갱신한다. 기존 코드 관찰인 MEDIUM이다.
- D3: code trace + 제한된 입력 재현 + 실제 GitHub 응답. MEDIUM confidence; 기존 코드 관찰인 LOW이다. `gh api 'repos/daeungo1/the-last-human/pulls?state=all&per_page=1'`의 키 존재 여부를 오케스트레이터도 확인했다.
- D4: 실제 함수 진단 + YAML 게시 경로, MEDIUM confidence; 기존 코드 관찰인 LOW이다.
- 라이브 답변→채점→체크와 보류 결과 댓글의 발생은 직접 관찰한 것이 아니다. 재현 입력과 코드 계약의 결함을 라이브 장애 이력으로 부풀리지 않는다.

### 품질 게이트

- **4 initial → 4 after gates → 4 verified [code: 4, inference: 0, assumption: 0]**. D3의 네 하위 결함은 하나의 집계 계약 발견으로 묶었다.
- 공식 action 입력 정의와 D1/D2의 핵심 인용을 오케스트레이터가 확인했다.
- 질문 JSON을 공개 Pages/댓글에서 다시 읽게 하는 대안은 정답·expected evidence 노출 위험 때문에 채택하지 않는다.
- 댓글 payload의 actor를 파싱하는 것만으로 신뢰된 확인자가 되는 것은 아니다. 먼저 발급 신뢰를 확인해야 한다.
- job summary/check-run output은 보류 데이터의 비영구 보관처로 인정하지 않는다.
- “변경량은 항상 양수여야 한다”는 조건은 삭제/이름 변경 등 모든 PR에 성립하지 않는다. 정확한 출처의 실제 값과 일치하는지를 완료 조건으로 삼는다.

### 발견 흐름

| --- | --- | --- |

| Gap | 11 → 6 → 4 | G1의 최종 고객/메시지 승인, G6의 외부 리소스·일정 조건 |
| Diagnosis | 4 → 4 → 4 | 실제 댓글 채점 런과 배포된 웹 흐름의 결과는 미관찰 |

서로 같은 경계를 다른 관점에서 다룬 결과이므로 세 단계의 건수를 더해 독립 결함 수로 표현하지 않는다.

### 세 가지 주제

**1. 제품이 약속할 것은 사람의 점수가 아니라 특정 변경에 남은 확인 근거다.**

S6·G1·G3을 함께 보면, 좋은 데모에는 질문 화면보다 “처음의 예상 → 실제 코드의 근거 → 필요한 수정 → 새 revision의 확인”이라는 연결이 필요하다. 현재 코드가 있는지와 확인자가 코드/영향을 설명했는지는 다르고, 확인 pass와 코드의 정확성도 다르다. 문항과 판단 기준은 사람이 직접 결정하며 기존 CI/리뷰를 대체한다고 말하지 않는다.

**2. 신뢰와 개인정보 경계는 UI 뒤로 미룰 수 없다.**

S2/S4·G2/G4·D1/D2/D4는 하나의 문제를 가리킨다. 지금의 공개 댓글 기반 입출력을 그대로 두고 화면만 직접 제출로 바꾸면 신원·질문 버전·보류 보존 문제가 해결되지 않는다. 기존 계획의 웹 제출 방향은 이 경계를 해결할 기회지만, 최종 schema·접근·수명은 아직 인간 승인이 필요하다.

**3. 대시보드는 장식이 아니라 같은 기록을 다른 각도에서 보여주는 결과여야 한다.**

S3·G5·D3은 마커 수정보다 넓다. 실제 사람의 신뢰된 성공 기록, 확인한 앵커, 머지 시점의 revision, 정확한 변경량을 연결해야 한다. “확인된 변경 비율”을 저장소 전체 이해도·안전도 또는 사람의 역량으로 바꾸어 말하지 않는다. 실제 1건 증분과 명시된 Demo data를 구분한다.

### 교차 단계 정합성 점검

- **상태 발급자와 최종 검증자를 구분해야 한다.** 새 계획은 backend App을 단일 status writer로 두지만(`friday-demo-plan.md:104,229-230`), 저장소 규칙은 Action의 위험 재계산과 현재 커밋 인증 확인을 요구한다(`.github/copilot-instructions.md:20-21`). 두 역할이 반드시 같은 프로세스일 필요는 없지만, writer 전환만으로 기존 독립 확인 책임까지 제거해도 된다는 뜻은 아니다. 구현 전에 이 책임이 어디서 충족되는지 명시해야 한다.
- **인간에게 맡겨진 정책을 기술적 수정으로 위장하지 않는다.** 1인 기본은 최신 제품 방향으로 전달하되 자격 조건·판정·schema의 최종 승인 없이 코드에 반영하지 않는다.
- **기존 경로의 결함을 전부 고친 후 새 경로를 만드는 순서가 자동으로 최선은 아니다.** legacy 댓글 경로를 종료할 계획이면, 현재 사용을 유지해야 하는 기간과 새 웹 경로의 전환 시점을 먼저 정해 중복 구현을 피한다.
- **진단이 제안한 저장 대안도 다시 걸러야 한다.** 공개 질문 JSON, actor 자기주장, job summary에 보류 저장은 각각 정답 보호·발급 신뢰·비보존 원칙을 충족하지 못한다.

### 아직 답하지 못한 부분

- 이번 주 팀이 이미 만들고 있는 별도 브랜치/백엔드, 사용 가능한 Azure/GitHub 리소스, 실제 담당과 가용시간.
- 인간 소유자가 승인한 질문 사례·판정 기준·성공 기록 형식과 데이터 수명.
- 실제 사용자에게 도움이 되는 정도와 실제 모델의 질문/판정 품질. 코드 구조만으로 학습 효과나 우승 가능성을 산정하지 않는다.

### 함께 진행할 설계 순서

1. **가치와 증거 확정:** 누구의 어떤 판단을 돕는지, 대표 PR에서 어떤 행동과 결과를 보여줄지 결정한다.
2. **실제 문항으로 판정 경계 확정:** 객관식·근거 설명·모르겠음·코드/설명 불일치의 기대 동작을 사람이 정한다.
3. **신원·revision·저장 책임 확정:** 위 결정을 지키는 최소 서버/Action 계약을 기존 팀 구현과 대조하고 인간 소유자의 승인을 받는다.
4. **한 경로의 완주와 촬영으로 연결:** 허가된 PR 하나의 웹 답변→현재 SHA의 상태→머지→모듈 집계가 이어지도록 하고, 그 다음 화면·영상의 완성도를 높인다.

이는 확정된 구현 계획이 아니라 위 미결 사항을 해소하기 위한 협의 순서다. 구현 저장소는 수정하지 않았다.

## User Decisions — 첫 설계 대화

사용자가 이번 대화에서 확인한 내용:

- **핵심 대상은 PR 작성자다.** AI 결과물도 사람이 책임져야 하며, 그 책임을 지기 위해 실제 동작과 영향을 알고 있어야 한다. The Last Human의 기록은 그에 필요한 내용을 확인했다는 증표가 되기를 기대한다.
- **대표 PR의 실제 3문항과 답변 사례를 보고 사용자가 판정 기준을 직접 정한다.** 현행 객관식/근거 AND 조건을 승인한 것은 아니다.
- **별도 진행한 구현은 아직 없다.** 현재는 아이디어 구체화 중이다.

이에 따라 제품 가설은 “AI 코드 탐지”나 “사람 평가”가 아니라 **작성자가 특정 revision의 동작·영향·선택 이유를 코드 근거로 설명하고 그 확인 기록을 남기는 흐름**으로 좁힌다. 이 기록만으로 무보조 답변, 완전한 이해, 코드의 무결함, 법적 책임의 충족을 보증하지 않는다.

### 초기 문항 사례 — 코드 근거 확인용으로 위치 변경

## Design Refinement — PR 목적과 구조가 먼저

### 사용자가 정정한 우선순위

사용자는 선택지/서술 모순의 판정 기준을 아직 선택하지 않았다. 그보다 먼저 다음을 구체화하도록 요청했다.

- 코드가 왜 있는지, 시스템의 구조와 전체 기능을 이해하는 것이 세부 코드 동작을 맞히는 것보다 중요하다.
- PR의 전체 내용에서 시작하여 변경이 retry와 관련된다는 것, 어떤 문제에서 retry하며 어떤 의도인지로 내려간다.
- PR 종류에 따라 질문 내용이 달라져야 한다.
- GitHub 연계와 Microsoft 생태계의 특별한 가치를 강조한다.

따라서 **코드 퀴즈 → 정답 판정**이 아니라 **변경 목적 → 시스템에서의 역할 → 유형별 의도·영향 → 필요한 코드 근거**의 순서로 설계 논의를 바꾼다. 이는 사용자의 제품 방향이며, 아래 분류와 질문 문구는 아직 협의용 제안이다.

### 질문 경험의 공통 뼈대

| 층위 | 알고 싶은 것 | retry PR의 협의용 질문 |
| --- | --- | --- |
| PR 목적 | 무엇을 해결하려는 변경인지 | 이 PR은 주문 서비스의 어떤 문제를 해결하려 하나요? 새로운 기능을 추가하는 것과 인증 갱신의 안정성을 높이는 것 중 어디에 가깝나요? |
| 기능·구조 | 변경이 전체 기능의 어디에 있고 누가 영향을 받는지 | 재시도하려는 것은 어떤 작업인가요? 토큰 갱신과 세션 이용 흐름은 어떻게 연결되고, 어느 부분이 이 변경의 영향을 받나요? |
| 의도·경계 | 왜 이 방식을 선택했고 어느 조건까지 적용하는지 | 어떤 종류의 갱신 실패를 일시적이라고 보나요? 재시도가 도움이 되지 않는 실패와 소진 시 동작은 어떻게 구분해야 하나요? |

세 문항이라는 기본값을 유지할 수 있지만, 이것이 최종 질문 생성 프롬프트나 세 개 조건의 고정 AND 판정이라는 뜻은 아니다. 실제 문항/판정 기준은 제품 소유자가 정한다.

코드 근거는 설명의 연결을 확인할 때 쓴다. 예를 들어 사용자가 “이 PR은 이미 재시도로 안정성을 높인다”고 설명했는데 코드에 재시도가 없다면, 목적과 구현이 다름을 짚는다. `fresh is token` 문법을 외우는 것을 주된 이해 기준으로 삼지는 않는다.

PR 제목·본문·연결된 요구사항은 **의도의 근거**, 코드·관련 호출자·테스트는 **실제 구현의 근거**다. 둘이 다를 때 PR 본문을 정답으로 취급하지 않는다. 요구사항이 없는 설계 이유는 기계가 만들어내서 사용자에게 맞히게 하지 않는다.

### PR 유형별 질문 관점 — 초기 제안, 확정 taxonomy 아님

| 변경 관점 | 전체 기능에서 물을 내용 | 이어서 물을 의도·영향 |
| --- | --- | --- |
| 기능 추가·동작 변경 | 어떤 사용자 작업이나 업무 흐름을 바꾸는가 | 바뀌는 입력·출력·업무 규칙과 기존 기능에 대한 영향 |
| 오류 수정·복원력 | 어떤 실패 상황을 해결하며 어느 계층이 처리하는가 | 재시도/복구가 유효한 조건, 반복하면 안 되는 상황, 실패 전달 |
| 권한·보안 | 누가 어떤 자원에 어떤 행동을 할 수 있게 바뀌는가 | 허용·거부 경계와 영향을 받는 호출 경로 |
| 데이터·스키마 | 어떤 데이터의 의미·보존·이동 방식을 바꾸는가 | 기존 데이터/소비자 호환성, 삭제 범위, 되돌릴 수 있는지 |
| 리팩터링·구조 변경 | 책임이나 의존관계를 왜 옮기는가 | 유지해야 할 외부 동작·계약, 영향을 받는 다른 모듈 |

- 유형은 배타적인 하나의 라벨이 아닐 수 있다. 주목적과 중요한 부수 영향을 나눌 수 있으며, 한 PR에 모든 유형의 질문을 강제하지 않는다.
- 유형별 질문은 위험도에 맞는 확인 내용을 선택하는 방법이지 위험 점수 규칙을 바꾸는 방법이 아니다.
- 문서 수정 등 임계값 미달 PR은 기존 neutral 경로를 유지한다. 질문 유형을 늘렸다고 모든 PR에 면담을 붙이지 않는다.
- 이 단계에서는 자동 분류 알고리즘·새 enum·가중치·프롬프트를 구현하지 않는다.

### GitHub와 Microsoft를 연결하는 가치

**제안 메시지: Copilot의 코드 작성 흐름을, 사람이 변경을 이해하고 책임지는 머지 흐름까지 연결한다.**

| 연결 지점 | 기존 플랫폼이 제공하는 것 | The Last Human이 추가하려는 것 |
| --- | --- | --- |
| GitHub Copilot | 저장소 조사·변경 작성·PR 생성/수정 작업 | 작성자가 PR 목적·구조·영향을 설명하고 코드와 대조하는 확인 경험 |
| GitHub PR/Actions/App | 변경 맥락, 커밋별 상태, required check와 발급 App 지정 | 해당 revision의 확인 결과를 머지 조건과 연결. 위험 재계산·SHA 결속은 유지 |
| Azure / Microsoft Foundry | 모델 운영과 AI 출력 품질 평가 도구 | PR 유형별 질문이 실제 요구사항·코드에 근거하는지 제품 개발 단계에서 평가 |

Microsoft만 기술적으로 가능한 API 조합이라는 주장은 하지 않는다. 공개 API로 다른 업체도 구현할 수 있다. 강조할 차별점은 **Copilot으로 시작한 개발 작업이 같은 GitHub PR에서 인간의 확인·머지까지 이어지는 경험**이다. Azure 로고를 추가하거나 Teams/Entra 기능을 무관하게 붙이는 것은 그 자체로 차별화가 아니다.

Foundry의 groundedness/relevance 등은 모델 출력 품질을 다루며 사람의 이해를 보증하는 점수가 아니다. 평가를 붙이더라도 인간이 검수한 합성/허가된 사례로 질문·판정 모델을 살피는 용도이며, 개인 보류 원문을 운영 추적에 저장하는 통로로 쓰지 않는다. 도입 여부는 아직 미확정이다.

공식 문서 확인:

- [GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent): 저장소 조사, 구현 변경, PR 생성/반복 작업. 실제 사용 가능 범위는 해당 플랜·권한에 따른다.
- [GitHub protected branches — required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging): 외부 서비스의 커밋 상태와 특정 GitHub App 발급자를 요구할 수 있다. 보호 설정과 bypass 권한에 따라 강제 범위가 달라진다.
- [Microsoft Foundry observability](https://learn.microsoft.com/azure/foundry/concepts/observability#core-observability-capabilities): 평가 대상은 AI 응답의 품질·신뢰성 등이다. 인간 이해 인증 기능을 제공한다는 뜻은 아니다.

책임 있는 AI 사용은 별도 추상 구호가 아니라 개발자의 실제 PR 작업에 구현된다. 제품의 가치는 코드에 연결된 확인 근거와 개발 경험으로 설명한다.
