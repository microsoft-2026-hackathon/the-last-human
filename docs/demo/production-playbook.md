# 데모 영상 제작 플레이북

v6 데모(88.5초)를 만들며 확정된 방식임. 다음 영상은 이 문서에서 시작하면 됨.
도구와 작업본은 `.work/demo-v6/`에 있고, 이 문서는 **왜 그렇게 했는지**와 **어디서 시간을 잃었는지**를 남김.

---

## 1. 파이프라인

```
스토리보드 ─▶ 대본(voice/cuts.json) ─▶ TTS(voice/tts.py) ─┐
                                                          ▼
raw 촬영(rec/drive.py) ─▶ CFR 프록시 ─▶ 박스 시트(edit/boxes.py) ─▶ 사람 확인
                                                          ▼
                              편집 스펙(edit/<take>.json) ─▶ render.py ─▶ out/<take>.mp4
                                                          ▼
                                              concat ─▶ out/T1-6.mp4
```

순서를 바꾸면 손해임. 특히 **박스 확인이 편집보다 먼저**고, **대본 확정이 편집보다 먼저**임.

## 2. 도구

| 파일 | 하는 일 |
| --- | --- |
| `rec/drive.py` | AppleScript로 Edge에 JS를 주입해 화면을 조작하고 `screencapture -v`로 녹화. 클릭 좌표·시각을 `events/<take>.json`에 기록 |
| `rec/edit/render.py` | 세그먼트 자르기·리타이밍·정지 프레임 → Pillow 오버레이 합성 → 나레이션 믹스 → `out/<take>.mp4` + 컨택트 시트 |
| `rec/edit/boxes.py` | **인코딩 없이** 박스 제안만 얹은 시트(`out/<take>-boxes.jpg`) 생성. 7초면 끝남 |
| `voice/tts.py` | Azure Speech(Entra 토큰). `--only N`으로 바뀐 컷만 재생성, sha 캐시로 나머지는 건너뜀 |

## 3. 시간을 크게 잃었던 것들

### 3.1 VFR raw와 렌더 타임라인의 어긋남 — 가장 비쌌음

`screencapture -v`가 만드는 `.mov`는 **VFR**임. `ffmpeg -ss <t> -i raw.mov`(입력 seek)로 뽑은 프레임이
`render.py`의 필터 체인(`fps=30,trim=start=…`)이 보는 같은 시각과 **최대 2~3초 어긋남.**

이걸 모르고 스크롤·상태 변화 시점을 재서 편집했다가 하이라이트가 전부 엉뚱한 화면에 얹혔고, 한 테이크를 통째로 다시 만들었음.

**규칙: 테이크마다 CFR 프록시를 먼저 만들고, 시각과 좌표는 프록시에서만 잼.**

```
ffmpeg -y -v error -i raw/<take>.mov -vf "fps=30,scale=1920:1080:flags=bilinear" \
  -c:v libx264 -preset veryfast -crf 20 -pix_fmt yuv420p proxy/<take>.mp4
```

프록시는 CFR이라 `-ss` seek이 정확하고, `render.py`가 보는 타임라인과 같음. `edit/boxes.py`도 프록시를 우선 씀.

### 3.2 events의 시각은 프록시보다 0.8~1.0초 빠름

`screencapture`가 뜨는 데 걸리는 시간 때문임. `events/<take>.json`의 `t`는 **참고만** 하고 실제 시각은 프록시에서 확인.
좌표는 반대로 신뢰해도 됨 — 뷰포트 pt 좌표이므로 **× (1920/1728)** 하면 출력 좌표가 됨.

### 3.3 프록시가 raw보다 짧을 수 있음

`t4d-checks.mov`는 raw 13초인데 프레임이 81장뿐이라 프록시가 5.67초에서 끝났음. VFR에서 정지 구간의 프레임이 거의 없었기 때문.
`in`/`out`을 raw 길이 기준으로 잡으면 빈 세그먼트가 나옴. **프록시 길이를 먼저 확인할 것.**

### 3.4 Retina 캡처의 좌표계

내장 디스플레이에서 1728×972 pt 영역을 녹화하면 **3456×1944 px**가 나옴. 출력은 1920×1080이므로
편집 스펙에 `"source_size": [3456, 1944]`를 넣어야 줌 계산이 맞음. **오버레이 좌표는 언제나 출력(1920×1080) 좌표계.**

### 3.5 "틀린 상태"가 안 찍히는 경우

T3에서 Q2의 **오답 보기가 한 프레임도 찍히지 않았음.** 정정 클릭이 화면 스크롤보다 먼저 일어나, 그 행이 보일 때는 이미 정답이었기 때문.
대사를 "보기가 틀렸다"에서 **"근거 문장이 틀렸다"**(실제로 화면에 남아 있는 것)로 바꿔 해결했음.

**촬영 스크립트에서 "보여 줄 상태 → 스크롤 → 잠깐 정지 → 상태 변경" 순서를 지킬 것.** 상태를 먼저 바꾸면 증거가 사라짐.

### 3.6 편집으로 못 살리는 정지 화면

T3 중반이 12.7초짜리 단일 정지 화면임. 필요한 상태(Hold + 틀린 근거)가 실촬로 1.0초뿐이라, 나머지는 정지 프레임으로 채울 수밖에 없었음.
**촬영할 때 읽을 것을 읽으면서 실제로 스크롤해 두면 편집이 훨씬 자유로워짐.**

## 4. 편집 규칙

### 4.1 나레이션이 마스터

- **TTS rate 0%. 배속은 어떤 경우에도 쓰지 않음.** 빠르게 느껴지면 대본을 줄임
- 쉼은 **컷 WAV를 문장 단위로 잘라 배치 간격으로** 만듦 (`audio`의 `from`/`to`/`at`)
- 문장 사이 쉼 **0.8초**, 컷 도입 **0.6초**, 끝 여운 **0.5초**

### 4.2 하이라이트

- 문장이 끝나면 **해제한 뒤** 스크롤. 스크롤 중 하이라이트 유지 금지
- 자막·콜아웃은 **나레이션에 있는 단어만** 사용
- 박스 좌표는 눈대중 금지. 프레임에 좌표 격자를 그려 읽거나 잉크·색상 프로파일을 스캔해 실측
  - 행 단위: **컨테이너 세로 테두리 기준 좌우 대칭** (예: GitHub 머지 박스 테두리 x=346/1253 → 박스 354–1245)
  - 세로 범위: 대상 잉크와 위아래 요소 잉크의 **중간점**
  - 배지처럼 작은 대상: **중심 기준 좌우 같은 거리** (예: Hold 배지 중심 (1374,382) → `[1334,362,1414,402]`)
  - 열 이름이 없으면 숫자가 안 읽힘 → **헤더까지 묶어서** 잡기도 함

### 4.3 이음새

- 페이지가 바뀌면 **컷**
- 같은 페이지 안은 **실제 스크롤 프레임**을 씀
- 같은 페이지인데 raw에 스크롤이 없을 때만 **0.3초 크로스페이드**(`xfade_in`, 테이크 앞머리 전용)
- 앞 테이크의 마지막 프레임과 뒤 테이크의 첫 프레임이 같으면 전환 효과 없이 그대로 이음

### 4.4 raw는 고치지 않음

`edit/<take>.json`만 고쳐 다시 렌더함. 합성이 필요하면(예: 화면 옆에 참고 패널) **새 소스 파일을 만들고** 원본은 그대로 둠.

## 5. 길이 관리 — 이번 영상의 핵심 학습

```
최종 길이 ≈ 음성 + 쉼 × (문장 수 − 테이크 수) + 테이크 수 × (도입 + 여운)
```

배속과 쉼 제거를 배제하면 **길이를 줄일 수 있는 곳은 대본뿐임.** 편집으로 줄이려 하면 시간만 쓰고 안 줄어듦.

이번에는 초안 28문장 98.0초에서 시작해 **19문장 88.5초**로 맞췄음. 뺀 기준은 하나 — **화면이 이미 말하는 문장부터.**

| 뺀 문장 | 이유 |
| --- | --- |
| `Why is merging blocked?` | 바로 다음 문장이 답함 |
| `For each one the author writes an answer and submits.` | 화면이 그대로 보여 줌 |
| `In this example there are two questions.` | 질문 카드 두 개가 보임 |
| `The corrected explanation is submitted again.` | 앞 컷이 이미 말함 |
| `Both answers are accepted.` | Accepted 배지 두 개가 보임 |
| `Then the line that retries.` | 화면이 `MAX_ATTEMPTS = 3`을 보여 줌 |
| `sorts repositories by risk` | **미구현 기능이라 삭제** |

문장을 뺄 때 **받을 말이 사라지지 않는지** 확인할 것. D05를 줄이면서 "`token.py`도 세 번 재시도한다"는 말이 사라져
D06의 `3 × 3 = 9`가 성립하지 않게 됐음 → 한 문장 안에서 두 개의 3을 모두 말하도록 고침.

## 6. 검토 절차

1. **박스 시트 먼저** — `edit/boxes.py`로 박스만 얹은 jpg를 만들어 사람이 확인·확정. 영상 렌더는 그 다음
2. **테이크 하나씩** 렌더 → 프레임을 떠서 자막·하이라이트·화면이 맞는지 **스스로 검증** → 사람 검토
3. 지적이 나오면 `edit/<take>.json`만 고쳐 재렌더. raw는 건드리지 않음
4. 전체가 끝나면 concat으로 합본을 만들어 **실측 길이**를 봄. 추정으로 판단하지 않음

병렬화: 테이크는 서로 독립이므로 2~3개씩 묶어 동시에 진행 가능. 박스 좌표가 이미 있으면 재편집은 빠름.

## 7. 정직성 규칙

- **없는 화면을 만들지 않음.** 찍히지 않은 상태는 대사를 바꿔서 해결함
- **없는 기능을 말하지 않음.** 대본이 화면보다 앞서면 문서에 적고 이슈로 등록함
- 데모 데이터는 **배지를 계속 노출**하되 하이라이트하지 않음
- 화면에 담지 않는 것: 사용하지 않는 계정 행, 무관한 프로젝트명·계정명, OAuth code/state, 토큰·환경 파일
  - 잘라낼 수 있으면 크롭이 최선(사이드바 제거), 안 되면 패치로 덮고 문서에 남김
- 인용은 원문 그대로 두고 맥락을 잘라내지 않음

## 8. 촬영 스크립트 작성 요령

- **정지 홀드 5초 금지.** 클릭·붙여넣기 중이 아니면 5초 이상 멈추지 않음
- 대기(`settle`)는 **1~2초.** 서버가 실제로 걸리는 구간(채점 등)만 예외
- 보여 줄 것을 **읽으면서 실제로 스크롤**해 둘 것 — 편집에서 정지 프레임을 쓰지 않아도 됨
- 상태를 바꾸기 전에 **바뀌기 전 상태를 먼저 화면에 띄우고 잠깐 정지**
- 진행 상황은 `rec/STATUS.md`에 즉시 기록
