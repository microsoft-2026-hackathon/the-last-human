왜 그 상태를 믿을 수 있나

게이트가 열리려면 서버의 영수증과 Actions가 따로 계산한 값이 맞아야 한다. 비밀은 서버에만 있고, 경계를 넘는 것은 단기 OIDC 신원과 메타데이터뿐이다.

데이터 흐름

#구간무엇이 움직이나
①GitHub → ActionsPR 열림 / 새 커밋이 Relay를 시작. 웹훅 수신자가 필요 없다
②Relay → ServerPR 메타데이터 · 재계산한 snapshot binding + OIDC 신원(repo · workflow · repo id)
②′Server ↔ Modeldiff 사실 → 질문 두 개 · 근거 한 줄 → 평가. GitHub 게시·머지 권한은 없다
③작성자 ↔ Server보기 + 근거 한 줄 → Accepted / Hold + 근거 발췌. 원문은 공개 PR에 남기지 않는다
④Serverhead SHA 등 현재 리비전에 묶인 성공 영수증. 새 커밋에 재사용하지 않는다
⑤Server → ActionsVerify dispatch — 신뢰된 runtime이 대상 PR을 읽어 snapshot·위험도를 재계산해 binding과 비교
⑤′Actions → Server재계산한 binding + OIDC로 검증 요청. 서버도 영수증·현재 PR·새 snapshot을 대조
⑥Server → GitHub상태 Awaiting → Human-verified / Not required · 카드 · 보조 Check
⑥′Actions → GitHub현재 SHA의 최신 gate status를 읽어 실제 성공 게시를 확인. 서버 응답만으로 끝내지 않는다
⑦Store + CODEOWNERS구역별 머지 전 확인 비율 · 답할 수 있는 사람 수 · 예외 · 근거 PR. 이름 없이 수만
⑧사람 → GitHubMerge. 봇은 절대 아니다
⑨조직 → Server대시보드 열람 — 다음에 에이전트를 어디까지 열지 판단

신뢰 경계 넷

경계무엇으로 증명하나
App installation ↔ Server선택 저장소에 한정된 installation token. App 개인키는 서버에만
GitHub ↔ Actions워크플로 실행 신원. pull_request_target이라 main의 정의만 실행된다
Actions ↔ ServerOIDC + binding 대조. 사전 공유한 장기 시크릿을 쓰지 않는다
사람 ↔ Server같은 App의 OAuth 로그인과 작성자 인가. 세션은 메모리 30분

정직하게 말할 것

Actions에도 단기 GitHub·OIDC 자격은 있다. "비밀이 전혀 없다"고 말하지 않는다
코드와 설명 근거는 모델에 전달된다. 민감정보 유입 방지와 모델 서비스의 보관 정책은 별도로 다룬다
영수증의 결속은 head SHA뿐 아니라 repo/PR · base SHA · 정책 · snapshot · 위험도 · 작성자 · installation · 질문 버전을 포함한다
Human-verified · sha는 화면 표현이다. SHA를 status 식별자에 붙이지 않는다
Relay의 대가 — 러너 기동 지연 20–40초 · Actions 분 사용 · 체크 목록에 한 줄 더
필수 status last-human/human-verified · 저위험은 commit status success · 보조 Check neutral · Required 적용은 저장소 보호 규칙 요약본: architecture-simple.html · 출처: storyboard-v4.md §7
