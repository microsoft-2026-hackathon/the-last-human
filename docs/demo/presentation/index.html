배포·확장성·보안 20점 08 · Architecture — PR 하나가 지나가는 길

gate를 여는 주체는 서버 하나, 검증하는 주체는 Actions입니다

왜 믿을 수 있습니까
서버가 "통과"라고 말해도 gate는 열리지 않습니다. Actions가 대상 PR을 다시 읽어 위험도와 snapshot을 재계산하고 receipt와 대조한 뒤에야 열립니다.
비밀은 어디에 있습니까
App private key · client secret · 모델 자격은 서버에만 둡니다. 경계를 넘는 것은 단기 OIDC 신원과 metadata뿐입니다.
모델의 권한은 무엇입니까
질문을 쓰고 근거 한 줄을 대조할 뿐입니다. GitHub 상태를 바꾸거나 merge를 승인하지 못합니다. 위험 점수는 모델을 부르지 않습니다.

데이터 흐름과 신뢰 경계

#구간무엇이 움직입니까
①GitHub → ActionsPR 열림 / 새 commit이 Relay를 시작합니다. webhook 수신자가 필요 없습니다
②Relay → Servermetadata · 재계산한 snapshot binding + OIDC 신원
②′Server ↔ Modeldiff 사실 → 질문 2개 · 근거 한 줄 → 평가. GitHub 권한은 없습니다
③작성자 ↔ Server보기 + 근거 → Accepted / Hold. 원문은 공개 PR에 남기지 않습니다
④Serverhead SHA에 묶인 receipt. 새 commit에 재사용하지 않습니다
⑤Server → ActionsVerify dispatch — snapshot · 위험도를 재계산해 binding과 비교합니다
⑤′Actions → Server재계산한 binding + OIDC로 검증을 요청합니다
⑥Server → GitHubstatus · card · 보조 Check. GitHub에 쓰는 것은 이 하나입니다
⑥′Actions → GitHub현재 SHA의 최신 gate status를 직접 확인합니다
⑦Store + CODEOWNERS구역별 커버리지 · 답할 수 있는 사람 수. 이름 없이 수만 셉니다
⑧사람 → GitHubMerge. bot은 하지 않습니다
⑨조직 → Serverdashboard 열람
신뢰 경계무엇으로 증명합니까
App installation ↔ Server선택 저장소에 한정된 installation token
GitHub ↔ Actions실행 신원 · pull_request_target은 main 정의만 실행합니다
Actions ↔ ServerOIDC + binding 대조. 장기 시크릿이 없습니다
사람 ↔ Server같은 App의 OAuth · 세션은 메모리 30분입니다
정직하게 말할 것
Actions에도 단기 GitHub · OIDC 자격은 있습니다. "비밀이 전혀 없다"고 말하지 않습니다
코드와 근거는 모델에 전달됩니다. 보관 정책은 별도로 다룹니다
receipt 결속은 head SHA뿐 아니라 repo/PR · base SHA · 정책 · snapshot · 위험도 · 작성자 · installation · 질문 버전을 포함합니다
서버 1대 = 저장소 1개 바인딩입니다 — 패키징에서 정리 중입니다

특히 장애가 비싸고 감사 대응이 필요한 곳입니다 — 금융 · 의료 · 인프라.
개인 개발자가 아니라 조직이 고객입니다
무엇이
승인 기록 자리에 이해 기록이 생깁니다
누가 눌렀는지가 아니라, 어느 모듈에 답할 수 있는 사람이 몇 명인지를 조직이 미리 압니다.
merge 전 · commit SHA 결속
얼마에
서버 1대와 파일 3개
기존 CI · review · branch protection을 바꾸지 않고 check 한 줄을 더합니다. 롤백은 변수 한 줄입니다.
작성자 부담은 PR당 두 문항
지금 조직이 치르는 비용
  • 장애 복구 때 "이 코드 누가 압니까"를 그 자리에서 찾는 시간
  • CODEOWNERS에 담당자가 적혀 있지만 그 코드를 이해한 사람은 아닌 격차
  • 불일치가 큰 AI PR의 승인율 28.3% · merge까지 3.5배 — 재작업 비용
약속하는 것 / 아닌 것
  • 약속: 위험한 변경은 사람의 설명 없이 merge되지 않습니다
  • 약속: 그 기록은 commit에 묶이고 새 commit엔 재사용되지 않습니다
  • 아님: 버그를 찾아 주지 않습니다. 코드 품질을 보증하지 않습니다. 사람을 평가하지 않습니다

부록 · Q&A — 제약과 다음 수

지금 어디까지 되고, 다음은 무엇입니까

현재 제약 — 숨기지 않습니다
  • 서버 1대 = 저장소 1개 바인딩입니다
  • 구조 분석은 Python 중심입니다
  • gate가 status와 보조 Check 두 줄로 보입니다 (권위는 status)
  • Relay가 대상 저장소에 TLH 소스를 설치해 재계산합니다 — 소스가 없는 저장소엔 별도 verifier가 필요합니다
  • 작성자 세션은 메모리 30분이라 서버 재시작 시 재로그인해야 합니다
  • 질문 생성은 모델 호출이라 드물게 정답 키가 틀린 세트가 나올 수 있습니다
다음 수 — 우선순위 순
  • 무조건 발동 경로 — 삭제형 고위험을 잡습니다 (슬라이드 07의 C안)
  • 버전 고정 verifier 패키지 — 소스 없는 저장소에 설치 템플릿으로 배포합니다
  • 다중 저장소 바인딩 · status와 Check를 한 줄로 통합
  • 구조 분석 언어 확장
  • PR-MCI 유형별 질문 템플릿 — 논문의 8개 유형을 질문 생성에 반영합니다
실패 방향의 일관성
사람이 답을 빠뜨리면 막습니다. 모델이나 연동이 죽으면 통과시킵니다. 인프라 장애로 사람을 막지 않습니다. 미통과는 failure가 아니라 pending입니다.
