승인은 기록된다.

"human control"은 선언이 아니라 설계 목표다. 설계 목표라면, 시스템 어딘가에 그것을 강제하는 지점이 있어야 한다.
MCP를 호출하고 · Context를 주입하고 · Agent를 만들고 · Loop를 돌린 결과물이 UI로 동작하는데,
그 내부 코드를 실제로 읽는 사람이 얼마나 될까

05 · Solution

방향을 뒤집는다 — 사람이 모델에게 답한다

모든 AI 리뷰 도구는 사람에게 설명을 전달합니다. 우리는 사람에게 설명을 요구합니다.

STEP 1
위험도 판정
중요 경로·변경량·위험 패턴을 순수 함수로 계산. 같은 입력이면 항상 같은 결과. AI 작성 여부는 보지 않는다
STEP 2
질문 생성
해당 hunk를 가리키는 질문. 오답도 저장소에 실재하는 것으로 만든다
STEP 3
설명 · 근거
보기를 고르는 데 그치지 않고 코드 어디가 근거인지 함께 받는다
STEP 4
커밋 결속
확인 기록을 현재 커밋 SHA에 묶는다. 새 커밋엔 재사용되지 않는다
게이트 판정은 결정적 규칙으로 계산하고, LLM은 질문 생성과 대조를 돕는 보조 수단이다.
risk.py — 모델을 부르지 않는다 · 모델은 GitHub 상태를 바꾸거나 머지를 승인하지 않는다

06 · Principles

요청받아도 만들지 않는 것

개인 점수·순위
팀 내 비교 화면, 리더보드, 팀장 조회 기능. 만드는 순간 감시 도구가 된다.

Not required

실패 방향에 일관성이 있다 — 사람이 답을 빠뜨리면 막고, 모델·연동이 죽으면 통과시킨다.

09 · Packaging — Quick start

새 저장소에 거는 데 필요한 것 — 세 갈래

A · 운영자
한 번만
  1. GitHub App 등록
  2. 서버 배포 (1 프로세스 + SQLite)
  3. /healthz · 모델 호출 확인
여기까지는 어떤 저장소에도 영향 없음
B · 저장소 관리자
저장소마다
  1. App 설치 → 서버에 바인딩
  2. 파일 3종을 PR 하나로
  3. 저장소 변수 · 첫 PR로 발행 확인
  4. 그다음에 필수 체크 지정
lasthuman-app.yml · .lasthuman.yml · CODEOWNERS
C · 작성자
PR마다
  1. 카드 링크로 로그인 (최초 1회)
  2. 두 문항에 답
  3. Human-verified → 사람이 머지
평소 PR 흐름에서 벗어나지 않음
순서를 바꿔 필수 체크를 먼저 걸면 발급자가 없어 머지가 영원히 막힌다. 롤백은 저장소 변수 한 줄과 보호 규칙 해제.

10 · Limits

우리가 못 잡는 것을 먼저 말한다

조용한 고위험 — "작다 = 안전"이 아니다
refactor(auth): 불필요한 None 체크 제거 −2줄
중요 경로위험 패턴변경량총점 / 임계값
+30+0+030 / 40
  • 인증 코드의 권한 검사를 지워도 게이트가 막지 않는다
원인은 구조적이다
그래서 무엇을 할까
  • A. 가중치 상향 — 인증 경로 오타 수정까지 발동하는 부작용
  • B. 삭제 전용 신호 — "지워진 코드로 막지 않는다" 원칙과 충돌
  • C. 무조건 발동 경로 — 기존 zeroCoverage 방식과 정합 · 선택
중요 경로 최고 가중치 30 < 임계값 40. 위험 패턴은 추가된 줄에만 걸려 삭제형 위험을 놓친다.
.lasthuman.yml 규칙으로 실제 계산 · python docs/demo/presentation/verify_claims.py 로 재현

11 · Closing

Superhuman을 많이 모은다고
Super Organization이 되는 것이 아니다

장애가 났을 때 가장 먼저 나오는 질문은 "이 코드, 누가 아나요?" 입니다. 그때 찾기 시작하면 이미 늦습니다.

머지 전 확인 게이트
위험한 변경에만 발동하고, 작성자의 설명을 코드 근거와 연결해 커밋에 결속한다.
WHAT WE BUILT
이해가 기록된다
모듈별로 "사람의 확인 근거가 남은 변경"의 비율이 쌓인다. 이름이 아니라 수다.
WHAT IT CHANGES
감시 도구가 아니다
감점·순위·팀장 조회는 요청받아도 만들지 않는다. 만드는 순간 다른 제품이 된다.
WHAT IT IS NOT

AI-generated code. Human-owned decisions.

왜 그 상태를 믿을 수 있나

#구간무엇이 움직이나
①GitHub → ActionsPR 열림 / 새 커밋이 Relay를 시작. 웹훅 수신자가 필요 없다
②Relay → Server메타데이터 · 재계산한 snapshot binding + OIDC 신원
②′Server ↔ Modeldiff 사실 → 질문 둘 · 근거 한 줄 → 평가. GitHub 권한 없음
③작성자 ↔ Server보기 + 근거 → Accepted / Hold. 원문은 공개 PR에 남기지 않는다
④Serverhead SHA에 묶인 영수증. 새 커밋에 재사용하지 않는다
⑤Server → ActionsVerify dispatch — snapshot·위험도를 재계산해 binding과 비교
⑤′Actions → Server재계산한 binding + OIDC로 검증 요청
⑥Server → GitHub상태 · 카드 · 보조 Check. GitHub에 쓰는 것은 이 하나
⑥′Actions → GitHub현재 SHA의 최신 gate status를 직접 확인
⑦Store + CODEOWNERS구역별 커버리지 · 답할 수 있는 사람 수. 이름 없이 수만
⑧사람 → GitHubMerge. 봇은 절대 아니다
⑨조직 → Server대시보드 열람
신뢰 경계무엇으로 증명하나
App installation ↔ Server선택 저장소에 한정된 installation token
GitHub ↔ Actions실행 신원 · pull_request_target은 main 정의만 실행
Actions ↔ ServerOIDC + binding 대조. 장기 시크릿 없음
사람 ↔ Server같은 App의 OAuth · 세션 메모리 30분
정직하게 말할 것
Actions에도 단기 GitHub·OIDC 자격은 있다. "비밀이 전혀 없다"고 말하지 않는다
코드와 근거는 모델에 전달된다. 보관 정책은 별도로 다룬다
서버 1대 = 저장소 1개 바인딩 — 패키징에서 정리 중
