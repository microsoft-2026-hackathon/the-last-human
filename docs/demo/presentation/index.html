05 · Solution

방향을 뒤집는다 — 사람이 모델에게 답한다

모든 AI 리뷰 도구는 사람에게 설명을 전달합니다. 우리는 사람에게 설명을 요구합니다.

STEP 1
위험도 판정
중요 경로·변경량·위험 패턴을 순수 함수로. AI 작성 여부는 보지 않는다
STEP 2
질문 생성
그 hunk를 가리키는 질문. 오답도 저장소에 실재하는 것으로
STEP 3
설명 · 근거
고르는 데 그치지 않고 코드 어디가 근거인지 받는다
STEP 4
커밋 결속
기록을 커밋 SHA에 묶는다. 새 커밋엔 재사용되지 않는다
언제 발동하나
·중요 경로 · 위험 패턴 · 변경량 · 테스트 삭제
·이해 보유자 0명 모듈은 무조건
·임계값 미달은 발동하지 않는다
무엇이 다른가
·판정은 결정적 규칙, 모델은 보조
·커밋 SHA 결속 — 새 커밋엔 무효
·통과만 기록, 감점은 남기지 않는다

새 저장소에 거는 데 필요한 것 — 세 갈래

A · 운영자
한 번만
  1. GitHub App 등록
  2. 서버 배포 (1 프로세스 + SQLite)
  3. /healthz · 모델 호출 확인
여기까지는 어떤 저장소에도 영향 없음
B · 저장소 관리자
저장소마다
  1. App 설치 → 서버에 바인딩
  2. 파일 3종을 PR 하나로
  3. 저장소 변수 · 첫 PR로 발행 확인
  4. 그다음에 필수 체크 지정
lasthuman-app.yml · .lasthuman.yml · CODEOWNERS
C · 작성자
PR마다
  1. 카드 링크로 로그인 (최초 1회)
  2. 두 문항에 답
  3. Human-verified → 사람이 머지
평소 PR 흐름에서 벗어나지 않음

10 · Limits

우리가 못 잡는 것을 먼저 말한다

조용한 고위험 — "작다 = 안전"이 아니다
refactor(auth): 불필요한 None 체크 제거 −2줄
중요 경로위험 패턴변경량총점 / 임계값
+30+0+030 / 40
  • 인증 코드의 권한 검사를 지워도 게이트가 막지 않는다
원인은 구조적이다
그래서 무엇을 할까
  • A. 가중치 상향 — 인증 경로 오타 수정까지 발동하는 부작용
  • B. 삭제 전용 신호 — "지워진 코드로 막지 않는다" 원칙과 충돌
  • C. 무조건 발동 경로 — 기존 zeroCoverage 방식과 정합 · 선택
중요 경로 최고 가중치 30 < 임계값 40. 위험 패턴은 추가된 줄에만 걸려 삭제형 위험을 놓친다.
.lasthuman.yml 규칙으로 실제 계산 · python docs/demo/presentation/verify_claims.py 로 재현

부록 · Q&A 전용 — 발표 3:30 예산에 포함하지 않음

왜 그 상태를 믿을 수 있나

#구간무엇이 움직이나
①GitHub → ActionsPR 열림 / 새 커밋이 Relay를 시작. 웹훅 수신자가 필요 없다
②Relay → Server메타데이터 · 재계산한 snapshot binding + OIDC 신원
②′Server ↔ Modeldiff 사실 → 질문 둘 · 근거 한 줄 → 평가. GitHub 권한 없음
③작성자 ↔ Server보기 + 근거 → Accepted / Hold. 원문은 공개 PR에 남기지 않는다
④Serverhead SHA에 묶인 영수증. 새 커밋에 재사용하지 않는다
⑤Server → ActionsVerify dispatch — snapshot·위험도를 재계산해 binding과 비교
⑤′Actions → Server재계산한 binding + OIDC로 검증 요청
⑥Server → GitHub상태 · 카드 · 보조 Check. GitHub에 쓰는 것은 이 하나
⑥′Actions → GitHub현재 SHA의 최신 gate status를 직접 확인
⑦Store + CODEOWNERS구역별 커버리지 · 답할 수 있는 사람 수. 이름 없이 수만
⑧사람 → GitHubMerge. 봇은 절대 아니다
⑨조직 → Server대시보드 열람
신뢰 경계무엇으로 증명하나
App installation ↔ Server선택 저장소에 한정된 installation token
GitHub ↔ Actions실행 신원 · pull_request_target은 main 정의만 실행
Actions ↔ ServerOIDC + binding 대조. 장기 시크릿 없음
사람 ↔ Server같은 App의 OAuth · 세션 메모리 30분
정직하게 말할 것
Actions에도 단기 GitHub·OIDC 자격은 있다. "비밀이 전혀 없다"고 말하지 않는다
코드와 근거는 모델에 전달된다. 보관 정책은 별도로 다룬다
서버 1대 = 저장소 1개 바인딩 — 패키징에서 정리 중
구조 분석은 Python 중심

부록 · Q&A — 고객과 가치

누가 쓰고, 무엇이 달라지나

누가
에이전트를 이미 도입한 엔지니어링 조직. 특히 장애가 비싸고 감사 대응이 필요한 곳 — 금융·의료·인프라.
개인 개발자가 아니라 조직이 고객
무엇이
승인 기록만 있던 자리에 이해 기록이 생긴다. 누가 눌렀는지가 아니라, 어느 모듈에 답할 수 있는 사람이 몇 명인지를 조직이 미리 안다.
머지 전 · 커밋 SHA에 결속
얼마에
서버 1대와 파일 3개. 기존 CI·리뷰·브랜치 보호를 바꾸지 않고 체크 한 줄을 더한다. 롤백은 변수 한 줄.
작성자 부담은 PR당 두 문항
지금 조직이 치르는 비용
  • 장애 복구 때 "이 코드 누가 아나요"를 그 자리에서 찾는 시간
  • 담당자가 CODEOWNERS에 적혀 있지만 그 코드를 이해한 사람은 아닌 격차
  • 리뷰에서는 94%가 낫다고 했는데 배포 뒤 78%가 장애 — 검토와 결과의 괴리
우리가 약속하는 것 / 아닌 것
  • 약속: 위험한 변경은 사람의 설명 없이 머지되지 않는다
  • 약속: 그 기록은 커밋에 묶이고 새 커밋엔 재사용되지 않는다
  • 아님: 버그를 찾아 주지 않는다. 코드 품질을 보증하지 않는다. 사람을 평가하지 않는다

지금 어디까지 되고, 다음은 무엇인가

현재 제약 — 숨기지 않는다
  • 서버 1대 = 저장소 1개 바인딩
  • 구조 분석은 Python 중심
  • 게이트가 status와 보조 Check 두 줄로 보임 (권위는 status)
  • Relay가 대상 저장소에 TLH 소스를 설치해 재계산 — 소스가 없는 저장소엔 별도 verifier 필요
  • 작성자 세션 메모리 30분 · 서버 재시작 시 재로그인
다음 수 — 우선순위 순
  • 무조건 발동 경로 — 삭제형 고위험을 잡는다 (슬라이드 10의 C안)
  • 버전 고정 verifier 패키지 — 소스 없는 저장소에 설치 템플릿으로
  • 다중 저장소 바인딩 · 한 줄 통합 체크
  • 구조 분석 언어 확장
배포
한 프로세스 + SQLite. 공개 HTTPS origin이면 바로, 사내망이면 self-hosted 러너 + 사내 접속으로. GitHub 웹훅 수신자가 아니라 가능하다.
