Ban or Check 05 · A check, not a ban

The industry answered with a ban. We answer with a check

Godot Engine · contribution policy 2026
AI cannot take responsibility
A decision to accept only contributions a person can answer for. Contributions the author does not understand are refused.
A ban is clear. It also throws away the productivity AI gives you.
The Last Human
We check understanding, not authorship
We do not rely on AI detection. We judge on the risk of the change alone, and only for risky changes do we ask the author to explain it from the code.
Instead of banning, we check only the risky changes and keep the understanding

Hypothesis → experiment
The more judgment a file carries, the more it stops us
  • risk.py · interview.py · attest.py → +30 each
  • Every time we touched those three, our own PR was asked to explain itself
Measurement → learning ①
We found what it misses
  • A deletion in an auth path scores 30 / 40 and never fires
  • The top critical-path weight sits below the threshold, and risk patterns match added lines only
  • A raise weights · B deletion signal · C always-fire paths ← chosen
Measurement → learning ②
We are not hiding this
  • 12 PRs were merged while the gate was still pending
  • During development we did not keep the required check switched on
  • We report that number as it is

Trust by Design 08 · Architecture — the path one PR travels

Only one server can open the gate. Actions is what verifies it

⑦The gate does not open just because the server says "pass." It opens only after Actions recomputes and matches.
🔒App private key · client secret · model credentials live on the server only. All that crosses the boundary is short-lived OIDC.
✕The model writes questions and checks evidence. It cannot write to GitHub and cannot merge.

At what cost

Adds one check line without touching existing CI · review · branch protection. Rollback is one variable.
The author’s cost is two questions per PR
What organizations pay today
  • Time spent mid-incident asking "who knows this code?" on the spot
  • The gap where CODEOWNERS names an owner who is not the person who understood the code
  • 28.3% approval and 3.5× time to merge on high-inconsistency AI PRs — the cost of rework
What we promise / what we do not
  • Promise: a risky change does not merge without a human explanation
  • Promise: that record binds to the commit and is never reused on a new one
  • Not: it does not find bugs. It does not guarantee code quality. It does not evaluate people

Appendix · Q&A — limits and next moves

What works today, and what comes next

Today’s limits — we do not hide them
  • One server binds to one repository
  • Structural analysis is Python-centric
  • The gate shows as two lines — a status and a helper Check (the status is authoritative)
  • The Relay installs TLH source in the target repo to recompute — repos without the source need a separate verifier
  • Author sessions live 30 minutes in memory, so a server restart forces re-login
  • Question generation is a model call, so a set with a wrong answer key can rarely slip through
Next moves — in priority order
  • Always-fire paths — catches high-risk deletions (option C on slide 07)
  • A version-pinned verifier package — shipped as an install template for repos without the source
  • Multi-repo binding · merging the status and the Check into one line
  • More languages in structural analysis
  • Question templates per PR-MCI type — folding the paper’s eight types into generation
Failure has a consistent direction
If a person skips the answer, it blocks. If the model or an integration dies, it lets through. Infrastructure failure never blocks a person. Not-yet-passed is pending, not failure.
